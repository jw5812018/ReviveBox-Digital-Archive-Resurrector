## 2. 产品定义

### 2.1 一句话

**EchoShelf brings your forgotten web back into view.**

一个由用户掌握数据的个人档案工具，把散落的浏览器书签、RSS 订阅和文本笔记整理成可搜索、可浏览、可重新发现的个人知识架。

### 2.2 用户与问题

目标用户是积累了很多资料的开发者、研究者和学生：保存过很多链接和笔记，却经常找不到或忘记回看。工具要解决“从已有收藏中找回有用内容”，让第一次使用的人几分钟内就能导入、找到并重新收藏一条资料。

### 2.3 Resurrection 的具体关联

复活经典个人网页门户、目录式收藏和早期个人 RSS 阅读器的使用体验：用户选择来源、拥有自己的目录、主动阅读。保留书签 HTML 与 OPML 等可迁移数据的价值，再加入统一搜索、去重、本地持久化和重新发现功能。

RSS 和 OPML 仍在使用，不要声称这些协议已经消失。作品介绍应具体解释重新设计了哪种旧式体验，并通过可运行的导入与阅读流程展示出来。不要只是给普通列表添加万圣节装饰。

### 2.4 明确边界

- “复活”指找回已经导入或成功获取过的内容，不承诺恢复从未保存、已经从网络消失的网页。
- 不抓取任意网站全文，不做互联网档案搜索，不绕过网站限制。
- 第一版无需账号、无需云端个人资料库、无需用户提供 AI API Key。
- 确定性逻辑由程序实现。解析、去重、搜索和排序不调用大模型。
- Kiro 用于开发过程；应用运行时不依赖 Kiro credits。
- 不做聊天助手、向量数据库、团队协作、浏览器扩展、移动端原生应用、计费系统或后台定时爬取。

## 3. 需要交付的最小完整版本

下列 R 编号应映射到正式规格、实现任务和相关验证。先完成必需项，再考虑加分项。

| 编号 | 必需功能 | 可观察的验收结果 |
| --- | --- | --- |
| R1 | 首次进入与示例库 | 新用户可以选择“Try the demo”或导入自己的文件；无需登录即可体验完整流程。 |
| R2 | 导入浏览器书签 HTML | 支持常见 Netscape Bookmark HTML 导出格式；读取标题、URL、文件夹路径，以及存在且有效的保存日期。 |

| R4 | 笔记与单条收藏 | 支持新建、编辑纯文本笔记，导入 .txt / .md 文件，以及添加一个有效链接；Markdown 第一版作为纯文本处理。 |

| R6 | 搜索、筛选与阅读 | 对标题、保存的摘要/笔记正文、标签和 URL 搜索；支持类型、标签、收藏、已读筛选；可以打开条目详情和外部原文。 |
| R7 | 本地保存与备份 | 刷新页面后内容和状态保留；支持带版本号的 JSON 导出与重新导入；清楚提示数据保存在当前浏览器，建议导出备份。 |
| R8 | Rediscover | 按公开的简单规则呈现较早保存且尚未阅读的条目；给出推荐原因，不伪装成 AI 判断。 |

### 3.1 输入限制与结果解释

- 每个本地输入文件上限 5 MiB，每次导入最多处理 1,000 条记录；超过限制时说明原因，不静默截断。
- 先解析和预览，再由用户确认写入。取消预览不改变数据。
- 非法 URL、缺失必要字段或无法解析的文件要给出可理解的错误。单条坏记录不应导致其他有效记录全部无法预览。
- 预览中的有效重复记录可以合并来源与标签，但不得覆盖用户已编辑的内容和阅读状态。
- OPML 只包含订阅信息，不能显示为“已导入文章”。导入订阅后提供单独的手动获取操作。
- 文件夹路径作为来源元信息保留；可把直接父文件夹转成一个初始标签，不强制把所有祖先文件夹都变成标签。
- 不读取整个硬盘，不扫描用户浏览历史，只处理用户明确选择的文件和输入。

### 3.2 链接与失效来源

- 第一版不自动批量检查所有外部书签是否失效。未检查的链接显示“Not checked”或不显示可用性结论。
- 订阅请求失败不能直接等同于“网站已死亡”；区分超时、HTTP 错误、格式无效和安全策略阻止。
- 详情显示实际保存的文本内容，以及原文链接。只有标题而没有正文的书签，应如实展示，不生成伪造摘要。

### 3.3 示例库

- 提供约 40–60 条原创示例内容，包含中英文、数个标签、不同日期，以及可用于展示去重的输入文件。
- 示例文件必须经过真实解析和入库流程，不能只在界面上写死结果数字。
- 示例库与个人库使用不同的 IndexedDB 数据库名，例如 echoshelf-demo 与 echoshelf-personal；重置示例库不能修改个人库。
- 示例中的 RSS 快照、虚构链接和内容明确标记为 Sample / Demo。示例回放不冒充实时网络获取。
- 提供可下载的示例书签 HTML、OPML、RSS/Atom 和文本文件，让评委可以亲自导入。
- 原创样例使用 example.org 等保留示例域名；真实在线订阅另外验证，不把示例域名作为真实可抓取来源。

## 4. 数据正确性

### 4.1 建议数据模型

保持模型精简，不为未来功能增加字段。至少覆盖：

- **Item**：id、kind（bookmark / article / note）、title、originalUrl、canonicalUrl、保存的正文或摘要、tags、sourceIds、createdAt、updatedAt、savedAt、readAt、starred、noteFingerprint（仅笔记需要）。
- **Source**：id、kind（bookmark-file / feed / note-file / manual / demo）、名称、feedUrl（若适用）、lastFetchedAt、最近一次获取状态。
- **导入结果**：输入记录数、新建数、重复数、无效数、逐条问题；不要求把所有导入日志永久写入数据库。

savedAt 使用可信的原始保存时间；缺失或无效时回退到本次导入时间，并在详情中说明日期来源。不要把刚导入就当作刚创建，也不要凭空推测旧链接年龄。

### 4.2 URL 规范化与去重

- 使用标准 URL 解析。内容链接仅接受 http / https；拒绝 javascript、data、file 等协议。
- 域名、协议采用标准规范化，移除默认端口和片段标识；去除明确列出的跟踪参数，如 utm_*、fbclid、gclid。
- 保留其他查询参数、重复参数、路径大小写与有意义的路径结构。不要默认合并 http 与 https、不同的 www 域名或尾斜杠。
- 保存原始 URL，用规范化 URL 作为带 URL 条目的去重依据；同一 URL 来自书签和订阅时可以保留多个来源。
- 导入合并必须保留稳定 id、用户标题、用户标签、用户笔记、收藏与已读状态；允许合并新的来源和标签。
- 纯文本笔记不按标题去重。采用明确定义的内容指纹，例如对统一换行与 Unicode NFC 后的标题及正文生成指纹；保留用户原始正文。
- 把去重策略写入设计和测试，不依赖 AI 猜测两篇内容是否相同。

### 4.3 Rediscover 规则

第一版用简单且可解释的规则：优先列出较早保存、尚未阅读的条目，稳定排序后选取少量卡片。默认可以用“保存超过 30 天且未读”；如果不足，回退到最早的未读条目并显示相应原因。

原因示例：“Saved 8 months ago · Unread”。没有候选时展示合理空态，不伪造历史。日期计算应可注入固定时钟，方便测试。

### 4.4 搜索与备份

- 第一版用本地确定性搜索即可：对字段做适当大小写/Unicode 规范化后匹配；支持中文连续文本，不只依赖英文分词。
- 多个筛选条件的组合逻辑写清楚。首版不做语义搜索、模糊纠错或搜索结果 AI 总结。
- 数据导出包含 schemaVersion、items、sources 和必要元信息；个人库与示例库分别导出。
- 恢复前校验版本、类型、URL 和关联 id；未知版本、损坏 JSON 或异常关联应在写入前拒绝。
- 明确采用“合并导入”策略；导出后导入空库应保留条目、标签、来源与状态。不能靠重新生成 id 破坏来源关系。
- 最终写入用事务保证一致性；存储失败应可见，不能先展示“成功”再丢数据。

## 5. 界面与体验

风格方向是“安静的数字档案馆”：温暖纸白背景、墨色文字、柔和的琥珀色强调、清晰的目录感。可以提供低调的暗色版本作为加分项，但优先完成一个精致主题。

首页不要只做营销介绍。首屏直接展示产品名称、用途、Try the demo 和 Import your collection 两个主要入口。

桌面采用侧边导航、内容列表与按需打开的详情面板：

- 导航：All items、Bookmarks、Articles、Notes、Starred、Rediscover，以及来源与标签。
- 内容区：搜索、筛选、排序、Import / Add 按钮、条目列表；提供真实记录数量。
- 详情：标题、来源、保存日期、标签、已保存正文、收藏/已读操作、外部链接。
- 窄屏：侧栏折叠为菜单，详情作为独立页面或抽屉，主要操作不能仅依赖悬停。

视觉细节可以把“找回一条收藏”表现为柔和的点亮或卡片展开，但不做强制长动画、全屏闪烁、自动音效或影响阅读的装饰。

使用语义化控件，保证可见焦点、可读对比度和有名称的图标按钮；支持 reduced-motion。对话框正确管理焦点，Esc 可以关闭，键盘与触屏都能操作。界面不展示内部调试字段或开发工具术语。

所有可点击按钮都要有真实功能。尚未实现的功能不要用成功提示冒充完成。

## 6. 默认技术方案

若工作区已有可靠技术栈，先说明差异并复用；当前空项目默认采用下列方案，不先扩展成多包平台：

| 部分 | 默认选择 | 原因 |
| --- | --- | --- |
| 客户端 | React + TypeScript + Vite | 适合桌面和手机浏览器，开发与部署流程简单。 |
| 样式 | 普通 CSS / CSS Modules，统一 CSS 变量 | 便于做一致的视觉设计，减少初始化依赖。 |
| 本地存储 | IndexedDB，使用 Dexie | 支持结构化数据与事务，个人资料不需要上传服务器。 |
| 服务端 | 小型 Node.js + Express 服务 | 提供受限制的订阅读取，并在生产环境提供前端静态文件。 |

## 7. 订阅读取与外部输入

任意订阅 URL 会让服务端向外请求，因此这部分必须在正式设计中说明边界并验证；不能直接对用户输入调用 fetch 后原样返回。

- 接口建议为 POST /api/feeds/fetch，接收一个 URL，返回标准化的订阅与条目；不提供任意网页代理。
- 首版实时获取仅接受公共 HTTPS 来源和标准 HTTPS 端口，拒绝 URL 内用户名密码、localhost、私网、回环、链路本地及保留 IP。
- DNS 解析结果需要校验 IPv4、IPv6、IPv4-mapped IPv6；实际连接必须使用已验证的地址，避免“验证后重新解析”产生差异。保持正常 TLS 证书校验。
- 重定向最多 3 次，每次都重新验证目标；不能用一次 URL 字符串检查代替整条请求链校验。
- 设置整个请求与读取过程的超时、并发和频率限制，例如总超时 8 秒、解压后响应上限 2 MiB、每次最多 200 篇；达到条目限制时清楚显示数量上限。
- 限制按流读取的实际字节数，不能只相信 Content-Length；拒绝不符合订阅格式的响应。
- XML 禁用外部实体与 DTD，来源 HTML 只提取可展示文本，第一版不渲染原始 HTML，不自动加载外部图片或脚本。
- 书签文件和订阅正文均为不可信数据。script 标签、事件属性、危险协议不得执行。外链采用安全的新窗口属性。
- 前端对同一来源防止重复刷新，服务端保持有限并发并处理取消；不要增加后台调度。

如果当前运行平台无法可靠约束网络目标，先只开放经过审核的固定订阅源允许列表，同时保留本地 RSS/Atom 文件导入。此降级必须在 UI、README、规格状态和演示中明示，不能宣称已支持任意在线订阅。不得以移除验证来“修好”请求失败。

## 8. Kiro 的实际开发流程与记录

### 8.1 正式规格

让 Kiro 根据本文件实际生成并维护：

1. `.kiro/specs/echoshelf-mvp/requirements.md`：用户故事与可验证的验收标准，必要时采用 EARS 格式。
2. `.kiro/specs/echoshelf-mvp/design.md`：架构、模型、导入流程、错误处理、网络边界、测试与部署方案。
3. `.kiro/specs/echoshelf-mvp/tasks.md`：按依赖排序的小任务，关联需求编号与验收方式；未实现或未验证的任务保持未完成。

不要把本文件直接复制成三份充当完成的规格。Kiro 应结合实际环境明确设计选择和任务划分。

### 8.2 Steering

用当前 Kiro 版本支持的格式建立精简的项目级 steering，覆盖：

- 产品：目标用户、Resurrection 关联、第一版边界、英文界面与中文内容支持。
- 技术：选定技术栈、目录、开发/测试命令、数据保存在本地。
- 质量：确定性去重、输入处理、真实状态与测试证据，不伪造功能和结果。

只有当前开发确实要遵循的规则才放入 steering；不要把所有笔记设成每次自动加载。

### 8.3 Hooks

优先实现一个真实有用的检查工作流：在手动触发或合适的任务结束点执行已存在的轻量检查命令，失败时展示真实结果。

先建立并手动验证 npm scripts，再通过 Kiro 当前版本的界面或官方格式创建 hook。不要凭空编造配置字段，也不要在尚未运行时声称已启用。确认触发一次、检查确实执行、失败能被看到；避免每保存一个文件就运行整套浏览器测试，避免检查结果触发自身形成循环。

如果当前版本不支持预期触发方式，就记录限制，选择受支持的手动 hook；不能以创建一个空配置文件代替工作流。

### 8.4 开发记录

在 `docs/kiro-build-log.md` 逐阶段记录日期、对应规格/任务、实际修改、运行过的检查、发现的问题和下一步。完成后从真实记录整理 `docs/kiro-usage.md`。

## 9. 分阶段实施与验收

每个阶段完成后，提供：改了什么、运行方法、验证结果、实际限制和下一步。失败先修复或明确阻塞，不把失败隐藏在“已完成”下面。

### 阶段 0：规格与环境

- 检查 Node、npm、Git 和现有目录，确定兼容版本。
- 按 Kiro 原生工作流完成需求、设计、任务及必要 steering。

## 10. 验证要求

给 package.json 提供清楚、非交互的命令，并让失败返回非零退出码：

```text
npm install          首次安装；提交锁文件后干净验证使用 npm ci
npm run dev          启动前端与必要的本地订阅服务
npm run lint         静态检查
npm run typecheck    TypeScript 类型检查
npm test             确定性的单元与集成测试，默认不访问互联网
npm run test:e2e     关键浏览器流程
npm run build        前端与服务端生产构建
npm start            启动生产构建
```

项目初始化时确定脚本的具体实现并验证；不要在 README 中列出不存在的脚本。

必须覆盖的有意义验证：

1. 同一输入导入两次，新建记录总数稳定；批次内部重复和库中已有重复均正确处理。
2. 规范化 URL 不随重复处理变化，保留有意义的不同查询参数和路径；规范化不会产生危险协议。
3. 合并重复条目不丢用户标签、编辑、已读/收藏状态和来源关系。
4. 中文笔记可搜索；空查询、无结果、多条件筛选有确定结果。
5. JSON 导出后导入空库保留数据与状态；损坏或不支持的备份版本在写入前被拒绝。
6. 刷新页面数据保留，重置示例库不影响个人库。
7. 恶意 HTML 不执行；脚本协议、外部实体、超大输入与不安全网络目标被拒绝。
8. 订阅超时/格式错误不会清空已保存条目，重复更新不制造重复文章。
9. 浏览器端完整路径：“进入示例 → 导入文件 → 查看去重结果 → 搜索 → 收藏 → 刷新验证 → 导出”。

可以用轻量性质测试验证两个真实不变量：`normalize(normalize(url)) = normalize(url)`，以及同一批数据重复导入后的条目集合不变。若使用 Kiro 的 Correctness/PBT 功能，记录它实际发现了什么；普通例子测试不能冒称性质测试。

测试以自制固定样例为主，日期使用固定时钟；不要依赖外站实时内容或机器当前时间。浏览器测试不能被纯截图替代，但视觉仍需人工或可用浏览器工具检查。

## 11. 三分钟以内的演示故事

目标视频时长约 2 分 40 秒，英文旁白或提供英文字幕，展示应用真实运行：

- **0:00–0:20**：展示一份杂乱旧收藏，说明目标用户及“存过却找不到”的问题。
- **0:20–0:55**：进入 EchoShelf，导入示例书签，展示真实预览、重复项处理和来源保留。
- **0:55–1:25**：搜索一个词，找到原先忘记的笔记/条目，进入详情并收藏。
- **1:25–1:50**：展示 Rediscover，说明基于保存时间和未读状态的推荐依据；展示一次订阅更新或清楚标注的本地样例回放。
- **1:50–2:20**：展示刷新后数据仍在、JSON 导出，以及个人资料保存在本地的实际设计。
- **2:20–2:40**：展示真实 Kiro 规格与一个实际运行的检查，解释规格和测试如何帮助解决一个具体问题。

演示素材以原创样例为主。不得使用未经许可的第三方音乐、商标素材或内容；不得剪辑出尚未完成的功能效果。
